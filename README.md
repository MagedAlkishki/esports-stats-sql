# esports-stats-sql

A normalized SQLite schema for a small competitive-FPS league — teams,
players, tournaments, best-of-N matches, individual map results, and
per-player per-match stat lines — plus a set of curated analytical
queries (win rates, K/D leaderboards, map strength, standings, player
form, head-to-head) and a test suite that checks every query's output
against an independently-computed expected answer.

## Why this exists

My other languages are Java, JavaScript, Python, PHP, C++, and C#; SQL is
the one skill that shows up in literally every one of those jobs and
rarely gets its own dedicated portfolio piece. Most "SQL practice"
projects are a single flat table with a few `SELECT`s. This one is
deliberately normalized — map results and player stats live in their own
tables, not bolted onto `matches` as extra columns — so the queries have
to do real joins, `GROUP BY`s, a window function, and in one case a
self-join, instead of reading one table with different `WHERE` clauses.
The dataset is esports-themed as a nod to my own background, but
everything else here is standard relational-SQL interview territory:
schema design, `CHECK`/`FOREIGN KEY` constraints, aggregation, and
analytical reporting queries.

## Schema

```
teams                one row per team
players              one row per player, FK -> teams
tournaments          one row per tournament/season
matches               one row per best-of-N match, FK -> tournaments, teams (x2)
                       team_a_score/team_b_score are MAPS won, not rounds
match_maps             one row per map played within a match, FK -> matches, teams
player_match_stats     one row per player per match (kills/deaths/assists), FK -> matches, players
```

Full DDL, including every `CHECK` and `UNIQUE` constraint, is in
[`schema/schema.sql`](schema/schema.sql).

## Seed data

[`seed/seed.sql`](seed/seed.sql) is deterministically generated by
[`scripts/generate_seed.py`](scripts/generate_seed.py) (`random.Random(42)`,
so re-running it with no code changes reproduces it byte-for-byte): 6
fictional teams across 4 regions, 30 players (5 per team, one of each
role), 2 tournaments each played as a full single round-robin among all 6
teams (30 matches total), best-of-3 map results, and a full stat line for
every player in every match they featured in (300 rows). The generator is
committed so the data's provenance is auditable, but it is **not** run by
the tests — the tests load the committed `seed.sql` directly, so the
dataset (and every expected test value) stays fixed.

## Queries

| File | What it answers |
|---|---|
| `queries/01_team_win_rates.sql` | Match win rate per team, across all tournaments |
| `queries/02_top_fraggers_by_kd.sql` | Top 10 players by career K/D ratio (min. 5 matches) |
| `queries/03_map_win_rates.sql` | Per-team, per-map win rate — each team's best/worst maps |
| `queries/04_tournament_standings.sql` | Points-table standings for one tournament (3 pts/win + 1 pt/map won) |
| `queries/05_player_form_last_5.sql` | Recent-5-match average kills vs. career average, per player |
| `queries/06_head_to_head.sql` | Every pair of teams that has played, with the won-lost split |

Run any of them directly:

```bash
sqlite3 -header -column esports_stats.sqlite < queries/01_team_win_rates.sql
```

## Building the database file

```bash
./scripts/build_db.sh
```

Produces `esports_stats.sqlite` (gitignored — it's a build artifact of
`schema.sql` + `seed.sql`, not something to track) that you can open in
any SQLite browser or query from the command line.

## Running the tests

```bash
python3 tests/test_queries.py
```

14 tests, using Python's stdlib `sqlite3` and `unittest` only — no
external dependencies. They split into two groups:

- **Schema integrity tests** — actually attempt invalid inserts (a
  foreign key to a nonexistent team, a role outside the allowed set, a
  team matched against itself, negative kills, a duplicate player stat
  line for one match) and assert SQLite rejects every one of them. This
  is the easiest kind of "SQL test" to skip — it's tempting to just trust
  the `CHECK`/`FOREIGN KEY` clauses — so these exist specifically to
  prove the constraints are wired correctly, not just declared.
- **Query correctness tests** — for each query, independently recompute
  the expected answer in Python straight from the raw rows (using
  `collections.Counter`, manual sorts, etc.), using different logic than
  the SQL query itself, then assert the two agree. For example, the win
  rate test rebuilds a `played`/`won` counter by walking every match row
  in Python and checks it against the query's `GROUP BY`/`SUM(CASE...)`
  output, rather than just checking the query runs and returns *a*
  number. This is meant to catch real bugs — a bad join that
  double-counts a map, a `HAVING` threshold that's off by one, a window
  function partitioned wrong — not just syntax errors.

## Project layout

```
schema/schema.sql          Table definitions, CHECK/FK/UNIQUE constraints
seed/seed.sql               Deterministically generated seed data (committed)
scripts/generate_seed.py    The generator that produced seed.sql (not run by tests)
scripts/build_db.sh         Builds esports_stats.sqlite from schema + seed
queries/*.sql               The six curated analytical queries, each documented above
tests/test_queries.py       Schema-integrity + query-correctness tests (stdlib only)
```
